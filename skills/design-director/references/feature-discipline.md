# Feature discipline and adoption

Use when a product is accumulating features, adoption is weak, navigation is overloaded, or a redesign risks turning into scope expansion.

## Feature cost model

A feature costs more than implementation. Evaluate:

- user cognitive load and discoverability cost;
- navigation/information-architecture pressure;
- interaction/state complexity;
- support and operational burden;
- maintenance/performance cost;
- fit with the core user/job;
- evidence that the feature creates meaningful value.

Rare use does not automatically mean "delete". Some features are low-frequency but high-criticality, compliance-required, seasonal, or role-specific.

## Build/keep test

For each feature, ask:

1. Which user/job does it serve?
2. What evidence says that problem matters?
3. Does it strengthen or dilute the product's core claim?
4. Can the capability be contextual rather than permanently visible?
5. What is the ongoing complexity cost?
6. What would happen if it were removed, merged, deferred, or made progressive?

## Adoption diagnosis

Low adoption can mean:

- low value;
- wrong audience;
- poor placement/timing;
- weak explanation;
- dependency/setup friction;
- discoverability failure;
- the feature solves an infrequent problem;
- instrumentation is wrong.

Do not treat "announce it harder" as the default fix.

## Attention budget

The interface has finite attention. Every persistent control or navigation item competes with the primary job. Use hierarchy, progressive disclosure, role/context, and search/command access to keep advanced capability available without making every feature equally loud.
