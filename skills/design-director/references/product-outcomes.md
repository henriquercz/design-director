# Product outcome layer

Use this reference when the request involves a SaaS/startup surface whose success depends on acquisition, activation, retention, expansion, monetization, or differentiation. This is an original routing layer; it does not replace a dedicated growth/CRO specialist.

## Dual outcome rule

A design decision should have two explicit outcomes when business performance is relevant:

- **user outcome** — what useful progress the person is trying to make;
- **product/business outcome** — the observable behavior that indicates the product delivered enough value to sustain the business.

Never improve the business outcome by making the user outcome materially worse through deception, obstruction, coercion, or accidental confusion.

## Outcome stages

Classify the dominant stage before optimizing:

- **Acquire** — help the right user understand relevance, trust the claim, and choose the next step.
- **Activate** — shorten the path from first entry to first meaningful value.
- **Retain** — make recurring value easy to recognize, repeat, recover, and resume.
- **Expand** — surface additional value when actual usage/context makes it relevant.
- **Monetize** — make price, plan boundaries, commitment, and upgrade consequences legible.
- **Differentiate** — make the product's mechanism, workflow fit, proof, and experience specific enough that it is not interchangeable.

The same interface can support several stages, but choose one dominant outcome for the current pass.

## Before visual treatment

For revenue-sensitive work, add these questions to prompt invariants:

1. Who is the intended user in buying/usage terms, not just demographics?
2. What situation triggered this visit/session?
3. What does the user already understand or believe?
4. What proof would reduce the main uncertainty?
5. What is the shortest honest path to useful value?
6. What measurable behavior would indicate success?
7. What guardrail metric would reveal harm or low-quality conversion?

If these are unknown, do not invent business performance claims. Treat them as hypotheses.

## Outcome-aware routing

- weak relevance/trust on a landing page → `voice` + `writing` + `relayout`, possibly external growth/CRO companion;
- confused first-run/empty state → `surface` + `interaction` + activation reference;
- users reach value but cannot repeat it → `surface` + retention/recovery work;
- pricing/upgrade confusion → monetization reference + `writing` + `interaction`;
- feature sprawl or weak adoption → feature-discipline reference + `surface`/`relayout`;
- visually polished but strategically interchangeable → `voice` + `refine push` + differentiation check;
- data exists but nobody knows what to do next → `surface` + `relayout` with action-oriented information hierarchy.

## Evidence loop

When outcome data exists, treat design changes as testable hypotheses:

`observed friction → hypothesis → smallest meaningful change → instrumentation/observation → decision`

Define before shipping:

- primary outcome metric;
- one or more guardrails (quality, completion, complaints, reversals, accessibility, retention, etc.);
- expected mechanism, not merely expected uplift;
- evidence confidence;
- rollback/reversal criteria when applicable.

Do not infer causality from a single before/after observation when other factors changed.

## Quality gate

Outcome-aware design succeeds only when:

- the user can tell what progress is being offered;
- the product does not obscure commitment, price, consequences, or exit;
- the primary action maps to a genuine next step;
- proof is specific and verifiable where possible;
- measured improvement is not bought by lower-quality users, hidden friction, or misleading behavior;
- the interface still meets Design Director's usability, accessibility, and visual-quality bars.
